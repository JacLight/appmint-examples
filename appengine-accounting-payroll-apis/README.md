# AppEngine Accounting and Payroll companion

A runnable finance client for journal posting, payroll calculation and configured approval, saved stubs/journals, private direct-deposit file generation, period close/reopen and draft W-2 creation. This is an AppEngine client, not a replacement payroll calculator. The server applies the business rules.

## Run

Use Node 24 or a current Node version with native fetch. No npm dependency installation is needed for the browser companion.

```sh
export APPENGINE_API_ORIGIN='https://YOUR_ASSIGNED_APPENGINE_ORIGIN'
export PORT=4113
node browser/server.mjs
```

Open the loopback address printed by the server. Sign in with your own organization and authorized finance staff account. The sample keeps sessions only in browser memory. Add a second named session for each approver you need; the selected name chooses a real existing session and grants no authority.

API Foundations covers account/backend discovery and staff authentication. Workforce APIs covers employee records, employee codes, payroll profiles and approved timesheets. Use your own training organization, branch, employee and an unused pay period. Do not reuse a period already processed for the same employee.

## Required records and policy

- Existing chart and automatic posting account map. The journal exercise uses account codes 1000 Cash and 6000 Rent; payroll resolves its configured expense, liability and cash codes.
- Employer readiness, hourly or salaried payroll profile, tax details, earning/deduction configuration and approved hours for the chosen period. Preview reports held pay and missing setup.
- Configured payroll-approval workflow with eligible approvers. Submit the calculated run, preserve its returned approval task ID and read task/stage progress after each decision. Do not edit run status directly.
- For ACH: bank-supplied organization originator settings plus the employee's verified deposit account/pay method. Do not invent bank details for actual payouts. The filmed example uses explicitly synthetic nonbank details and never transmits its private artifact.

## Follow the application

1. Accounts & readiness: enter the saved location name, employee code, period and pay date. Load the chart, automatic map and employer/profile status.
2. Journal & ledger: create one balanced draft. Read its ledger before posting; post that same saved ID and read the changed result.
3. Payroll calculation: preview, inspect missing/held entries, create one draft and calculate it. Preview and run totals use different response field names; the client normalizes only the display.
4. Review & approval: submit the run. Each assigned approver signs in separately, reads the task and decides. Required decisions come from the workflow. Read the resulting run status.
5. Stubs & bank file: process only the approved run, then read the actual saved stubs and linked payroll journal. Generate a payslip PDF. Processing records payroll; it does not prove bank settlement.
6. Direct-deposit setup: inspect existing originator configuration without printing private identifiers; save the employee's account and select direct deposit. Then generate the file and inspect count, total, reuse and effective-date adjustment. Generated bytes are deliberately excluded from the response inspector. A real product must secure any download separately.
7. Period & year end: review checks for the chosen ended month, lock with proper authority, and reopen with an audited reason when appropriate. A closed state does not prove reconciliation. Generate the employee's W-2 draft; compare included-stub count and totals before any separate filing workflow.

The sample’s September 2026 dates are editable for the pay run; journal/period report demonstrations use September 2026. Change all period filters together for your own exercise. Before closing a month, coordinate with its owner; the lock is organization-wide, not branch-only.

## Deliberate boundaries

The proxy allowlist excludes online ACH pay, tax filing/transmission, arbitrary provider calls and general-purpose URL forwarding. It binds to loopback for development. It is not a deployed authentication gateway. Do not expose it publicly without production authentication, origin policy, rate limits and review of finance authority.

No keys, accounts, credentials, training identities or private fixtures ship with this source. No payroll payment is transmitted. Generated payroll, tax and bank documents contain private information; do not commit them.

The recorded recovery checks reject premature processing and repeated processing while preserving the saved run/stub. Reconciliation, ACH returns/reissues, voiding and tax filing are separate linked reference procedures, not claimed completed demonstrations in this sample.

## Portable clients

Set `APPENGINE_API_ORIGIN`, `APPENGINE_ORG_ID` and `STAFF_TOKEN` in your environment. Start with read-only `node client.mjs accounts`, `python3 client.py accounts`, or `sh curl.sh`. `operations.json` contains 31 explicit named operations and their required placeholders. Export the selected operation’s values (for example `EMPLOYEE_CODE`, `RUN_ID`, `TASK_ID`, `PERIOD_START`, `PERIOD_END`, `PAY_DATE`, `LOCATION_NAME`) before running it. The clients execute only the operation you name; they never automatically approve, process or close anything.

For an approval decision, replace `STAFF_TOKEN` with the assigned approver’s session and retain the same organization and task ID. Return to the finance operator’s session for processing. Never copy a token into an operation body or committed environment file.

Import `postman.collection.json` into Postman. Supply credentials in a private local environment; requests inherit bearer authorization. `client.ts` illustrates typed composition and can be checked with `tsc -p tsconfig.json`. All 31 routes remain available through the JavaScript/Python operation runner and Postman, including the paired readbacks.
